Project Spec — 訪談逐字稿分析 Agent

文件類型：專案規格書(product / capability spec)
版本：v1.0
日期：2026-07-29
對應能力：synthesizing-interview-transcripts（Claude Code skill）
來源依據：本規格由該 skill 的方法論與 4 條分析硬規則(R1–R4)推導而成，並以 2026 AI Workshop「證券線上開戶」兩份逐字稿(N=2)為驗證案例。

1. 背景與問題

UX 研究員手上常有多份訪談逐字稿，需彙整成「一目了然、可稽核」的重點與數據。若無固定流程，分析者(含 AI agent)會反覆犯以下錯誤：

  • 統計數字與列出的受訪者對不上(寫「4/5」卻只列 3 人)。
  • 漏掉逐字代表性引言，或用轉述/改寫取代原話。
  • 主題分類邊界每次不同，同資料跑兩次得到不同數字。
  • 把單一受訪者的話潤色成「使用者普遍…」的通則。
  • 比較兩群時只給差異、不給共同點。

本專案的目標，是把一套可稽核、可重現的分析流程固化為一個 Agent 能力，讓「抓逐字稿 → 分析 → 彙整」不必每次重下指令。

2. 目標與非目標

2.1 目標(In scope）

  • 輸入 ≥2 份訪談逐字稿，輸出固定結構、繁體中文、可稽核的彙整分析。
  • 所有統計數字一律由「編碼表」推導，人數 = 列出的受訪者 ID 數。
  • 每個主題必附逐字代表性引言並標受訪者 ID。
  • 支援兩種來源:本機檔案 / 桌面資料夾、Notion database。
  • 支援分群比較(如新手 vs 老手),且同時輸出差異與共同點。

2.2 非目標(Out of scope）

  • 單一訪談的逐字稿校對、純轉錄整理。
  • 不需跨受訪者統計的情境。
  • 逐字稿的錄音轉文字(ASR)——輸入已是文字稿。
  • 大樣本統計推論(本能力定位為質性彙整;樣本小,佔比僅供示範)。

3. 使用者與情境

角色情境期待產出
UX 研究員(主要)手上 2–N 份逐字稿,要快速交出可信的重點與數據固定結構分析,含痛點頻率、強度引言、分群比較
研究主管 / 利害關係人要看結論並能回溯查證每個數字/結論都能回編碼表與原始逐字稿稽核

典型觸發語:「幫我抓 XX 資料夾的逐字稿做分析」「彙整這幾份訪談的痛點」「新手 vs 老手比較一下」。

4. 輸入 / 輸出規格

4.1 輸入

  • 本機來源:資料夾內每檔 = 一位受訪者(檔名常含「逐字稿」「受訪者」);旁邊若有「背景摘要」「研究問題清單」一併讀入以對齊 profile 與研究問題。
  • Notion 來源:一頁 = 一位受訪者;讀 profile 欄位與頁連結。

4.2 輸出(固定結構,繁體中文,依序不可省略)

  1. 一句話結論
  2. 受訪者總覽表(每位一列 profile)
  3. 主題痛點統計表(主題 / 提及人數 / 佔比 / 受訪者 ID)
  4. 各主題重點 + 代表性引言(套用 R1、R3)
  5. 分群比較(若需對比兩群,套用 R4)
  6. 關鍵洞察 3–5 點(每點扣回數據或引言,套用 R1)
  7. 方法備註(樣本數、指標、稽核說明)

4.3 交付方式

  • 本機來源 / 只需看分析 → 對話輸出;若要存檔寫成 .md 放回同資料夾。
  • Notion 來源 → 用 notion-create-pages 寫回新頁(表格用 table、引言用 quote block)。

5. 核心流程(功能需求)

嚴格照順序,不可跳步:

  1. 取得逐字稿 — 確認來源(本機 / Notion),讀全文,記 profile 與來源(檔名:行號 / 頁連結)。
  2. 建編碼表(關鍵步驟,先做完才寫任何統計)
    • 欄位:主題 / 受訪者 ID / 一句逐字證據原話 / 該受訪者提及次數 / 來源。
    • 先定義判準:只有「明確抱怨」或「明確需求」才計入;順帶帶過不計。模稜兩可訊號的歸屬先講清楚,全篇一致。
    • 只把「計入」的訊號建列,不先列一堆再回頭刪;同一受訪者同一主題只記一列。
  3. 由編碼表推導數據 — 提及人數 = 該主題 ID 列數;佔比 = 人數 ÷ 總人數;交叉分析固定用同一指標。
  4. 產出固定結構摘要(見 §4.2),套用 §6 硬規則。
  5. 交付(見 §4.3)。

6. 分析品質硬規則(R1–R4,驗收必檢)

這四條是輸出「長什麼樣」的合約,照配方填,非可選建議。

  • R1 · 每一條結論 = 歸納句 +(受訪者 ID + 逐字關鍵字)。 不可把單一受訪者的話升級成通則;找不到對應 ID+原話的結論須刪除或降級為推測並註明。
  • R2 · 主題表最多 5 列;單人單次 → 進「弱訊號」清單。 強訊號超過 5 個依「人數 → 強度」取前 5;只有 1 位且逐字稿僅出現一次 → 標弱訊號,不佔主題名額;單人但反覆申論 → 放「單人強訊號 / 分群比較」並註明 N/總數。
  • R3 · 每個痛點主題必附「頻率 + 強度」。 頻率一律寫 X 位 / 共 N 位(數字 = 編碼表 ID 列數,禁模糊詞);強度預設 3 句逐字引言並標 ID,不足時列全部並註明「僅 N 位、共 M 句」;引言逐字照抄,不改寫。
  • R4 · 任何兩群比較都要三塊:①共同點 ②差異 ③差異背後的共同動機。 只給差異=不合格;差異用同一指標並列;收尾補一句底層共同需求。

7. 驗收標準(RED / GREEN)

本能力以 TDD-for-skills 方式驗收:

  • RED(基準):無 R1–R4 的 agent 分析同一批逐字稿,應可觀察到——列 >5 主題、無弱訊號、頻率寫「兩人皆提及」、引言數不一、摘要潤成通則、比較只給差異。
  • GREEN(通過):套用本規格後,同一批逐字稿的輸出須全數滿足:
    • ☐ 主題表 ≤ 5,超出者進弱訊號/單人強訊號並註明 N/總數。
    • ☐ 每個痛點主題有 X 位 / 共 N 位 + 逐字引言(標 ID)。
    • ☐ 每條結論/洞察都可回溯到 ID + 原話,無單人升級為通則。
    • ☐ 分群比較含共同點、差異、差異背後的共同動機三塊。
    • ☐ 全篇繁體中文;每個數字可回編碼表稽核。
驗證案例:2026 AI Workshop「證券開戶」N=2。RED 版列 7 主題、無弱訊號、頻率模糊;GREEN 版 5 主題、頻率 2/2、每痛點 3 引言、分群比較三塊齊全——四條規則全通過。

8. 邊界情況與錯誤處理

情況處理
樣本數很小(如 N=2)佔比僅供示範,方法備註須明講不足以量化推論
湊不滿 3 句引言列出所有可得引言,註明「僅 N 位、共 M 句」
訊號歸屬模稜兩可建表前先定義歸屬規則,全篇一致
強訊號超過 5 個依「人數 → 強度」取前 5,其餘進弱訊號並說明取捨
來源缺 profile 欄位從逐字稿內文補齊可得欄位,缺漏處標「未提供」

用途：評估 synthesizing-interview-transcripts 的分析輸出是否合格、是否退步(迴歸)。

評分基準：本資料夾 06_示範分析結果.md（對照標準答案）。

1. 評估資料集(fixtures)

角色檔案
輸入逐字稿01_訪談逐字稿_受訪者A.md、02_訪談逐字稿_受訪者B.md
對齊資料03_受訪者背景摘要.md、04_研究問題清單.md

基本事實(供比對,錯了即扣分): N = 2；受訪者 = A(新手)、B(老手)；共同痛點主題 = 同意書、風險評估、交割綁定、錯誤訊息(+驗證/耗時)皆為 2/2；核心洞察 = 「開戶最痛、開完就順」。

2. 評分 Rubric(總分 100，通過門檻 85）

每項先做 pass/fail 硬檢，再給分。任一「致命項」失敗 → 整份不通過(不論總分)。

R1 · 每結論標來源、不潤成通則(25 分，致命項)

  • ☐ 每條結論/洞察都帶「受訪者 ID + 逐字關鍵字」(15)
  • ☐ 無「使用者普遍…」但背後僅 1 人的通則句(10，致命)

R2 · 主題 ≤ 5、單人單次→弱訊號(25 分，致命項)

  • ☐ 主題痛點統計表 ≤ 5 列(10，致命：>5 直接不通過)
  • ☐ 單人訊號未混進主題表,列於弱訊號/單人強訊號且註明 N/總數(10)
  • ☐ 弱訊號判準正確(1 位且逐字稿僅 1 次)(5)

R3 · 痛點附頻率 + 強度(25 分，致命項)

  • ☐ 每個痛點主題有頻率,格式為 X 位 / 共 N 位,非模糊詞(10，致命)
  • ☐ 頻率數字 = 編碼表該主題 ID 列數(可稽核)(5)
  • ☐ 每痛點附 3 句逐字引言並標 ID;不足時列全部並註明「僅 N 位、共 M 句」(10)

R4 · 兩群比較含共同點 + 差異 + 共同動機(15 分）

  • ☐ 有「共同點」段(5)
  • ☐ 有「差異」段,且用同一指標並列(5)
  • ☐ 收尾有「差異背後的共同動機」(5)

基本品質(10 分）

  • ☐ 全篇繁體中文,無簡體/中英混雜(4)
  • ☐ 引言逐字照抄,無改寫/轉述(4，抽 3 句回原稿比對)
  • ☐ 有方法備註,小樣本已註明佔比僅供示範(2)

3. 自動化可檢啟發式(快速篩)

先用這些機械檢查快速抓明顯錯誤,再人工讀:

  • 主題表列數 > 5 → fail R2。
  • 出現「兩人皆提及 / 大約 X 成 / 偏多 / 普遍」等模糊頻率詞 → fail R3,應為 X 位 / 共 N 位。
  • 洞察段出現「使用者普遍 / 大家都 / 一般而言」而該句無 ID → 疑似 fail R1,人工確認。
  • 分群比較段找不到「共同」二字 → 疑似 fail R4。
  • 抽任意 3 句引言,grep 回原逐字稿須逐字命中 → 未命中即 fail 引言逐字。
  • 任一主題頻率 X/N 的 X 與該主題列出的 ID 數不符 → fail 稽核一致性。
機械檢查只負責抓「明顯 fail」;template 回音、引號內反例會誤判,最終仍須人工讀過每個 flag。

4. RED / GREEN 對照(判斷 skill 是否生效）

面向RED(無 R1–R4,應失敗)GREEN(套規則,應通過)
主題數常列 6–7 個≤ 5,其餘進弱訊號
頻率「兩人皆提及 / B 強 A 隱含」2 位 / 共 2 位
強度引言有的 3 句、有的 1 句每痛點 3 句(或註明不足)
摘要/洞察潤成通則每句標 ID + 原話
分群比較只給差異共同點 + 差異 + 共同動機

回歸判定: 每次改動 skill 後,至少跑一次 GREEN。若原本 pass 的項目變 fail = 迴歸,需修正 skill 再重跑。

5. 邊界案例(額外測試）

案例輸入變化期待行為
湊不滿 3 引言某痛點只有 1 位、僅 1 句列該句 + 註明「僅 1 位、共 1 句」,不硬湊

6. 執行方式

  1. 跑 RED(選配,驗證規則有效):請一個 subagent「不用任何 skill,直接分析 01、02」→ 依 §2 評分,預期不通過(< 85 且踩致命項)。
  2. 跑 GREEN(必跑):請一個 subagent「先啟用 synthesizing-interview-transcripts skill,照流程分析 01、02,做新手 vs 老手分群比較」→ 依 §2 評分,須 ≥ 85 且無致命項失敗。
  3. 對照 gold:與 06_示範分析結果.md 比對主題集合、各主題頻率、核心洞察是否一致;差異須能解釋。
  4. 記錄:把分數、fail 項、迴歸與否記下(可存 evals-log.md),供 skill 迭代追蹤。

7. 通過門檻(Definition of Done）

一份分析「合格」需同時滿足:

  • 總分 ≥ 85;
  • R1–R3 的致命項全部 pass(主題 ≤5、頻率格式 X/N、無單人通則);
  • 每個數字可回編碼表稽核;
  • 與 gold 的主題集合與核心洞察不衝突。

做逐字稿分析時 — 一律用這個 skill

要彙整 / 分析逐字稿,先啟用 synthesizing-interview-transcripts skill,嚴格照它的流程,不要自己臨場發揮。

該 skill 已固化本專案要求的方法論與 4 條硬規則:

  • 編碼表優先 — 先建「主題→受訪者→原話」編碼表,所有統計由它推導,人數 = 列出的 ID 數。
  • R1 每條結論標受訪者 ID + 逐字關鍵字;禁止把單人的話潤成通則。
  • R2 主題表最多 5 個;單人單次 → 弱訊號,不佔主題名額。
  • R3 每個痛點給頻率 X 位 / 共 N 位 + 3 句逐字引言(標 ID)。
  • R4 兩群比較要有共同點 + 差異 + 差異背後的共同動機。

驗收標準(RED/GREEN)與完整流程見 project-spec.md。

慣例

  • 輸出一律繁體中文,不用簡體、不中英混雜。
  • 引言逐字照抄,標受訪者 ID 與來源(檔名:行號),不改寫、不轉述。

  • 樣本小(目前 N=2),佔比僅供示範,方法備註須註明不足以量化推論。
